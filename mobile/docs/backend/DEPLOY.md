# Luna: environments, deploy and backups

Written **27 September 2026** on branch `backend/hardening`. Nothing in this file has been run against a hosted
project yet, because none exists. Every remote step (linking, pushing, deploying, setting secrets) needs Donovan's
approval at the time it runs (HANDOFF §10). The audit behind it is in [`STAGING_PLAN.md`](STAGING_PLAN.md).

All commands run from `mobile/`.

## 1. Environments at a glance

| Profile | Backend | App settings file | Start the app |
|---|---|---|---|
| `local` (default) | Docker stack in `local-backend/` | `.env.local`, written by `npm run backend:env` | `npm run start:local` |
| `staging` | Hosted Supabase project | `.env.staging`, a copy of `.env.example` you fill in | `npm run start:staging` |

**How it works.**
1. `APP_ENV` picks the profile. `app.config.js` reads that profile's file.
2. It hands the public values to the app as `extra.backend`.
3. The app reads them through `src/utils/env.ts`. No code changes between environments.
4. Values in the profile file win over anything already in the environment. On CI or EAS, where there is no profile
   file, the build environment is used instead: set `APP_ENV` and the `EXPO_PUBLIC_*` variables there.

**Guards in `app.config.js`.** The build fails if:
- `APP_ENV` is anything other than `local` or `staging`.
- A staging run has no `.env.staging`, outside CI/EAS. This stops the old plain `.env`, which still names the
  deleted project, from sneaking in.
- The staging URL is not `https` or points at a local address.
- The staging URL or publishable key is missing.
- The local profile points at a hosted URL.
- `EXPO_PUBLIC_PET_TALK_PREVIEW` is set on staging.
- Any value is a service-role JWT or an `sb_secret_` key.

> **Always build with `--clear` after switching profiles.** Metro caches the app config and env values it bakes into
> web bundles. On 27 Sep a plain "local" export came out carrying the staging URL. `npm run start:local`,
> `npm run start:staging` and `npm run export:web` all add `--clear` for you. For anything else, add it yourself:
>
> ```bash
> APP_ENV=staging npx expo export --platform web --clear      # bash
> $env:APP_ENV="staging"; npx expo export --platform web --clear   # PowerShell
> APP_ENV=staging npm run start:phone -- --clear              # phone on the LAN, staging backend
> ```

## 2. Env files

| File | Committed? | Holds |
|---|---|---|
| `mobile/.env.example` | yes | Every public app variable, documented, with no values |
| `mobile/.env.local` | no | Local profile, generated by `npm run backend:env` |
| `mobile/.env.staging` | no | Staging profile: URL and publishable (anon) key |
| `mobile/supabase/functions/.env.example` | yes | Every Edge Function secret, documented, with no values |
| `mobile/supabase/functions/.env.staging` | no | Staging function secrets (the OpenAI key) |

Every `.env*` file except the two examples is gitignored (`mobile/.gitignore`), and so is `mobile/backups/`.

The app bundle may only contain the publishable key. The service-role key, the database password and provider keys
are server secrets: they go to Supabase with `functions:secrets`, never into an app env file.

## 3. The npm scripts

These four do nothing except call the Supabase CLI. Each pins `--workdir local-backend`, the folder that holds the
27 generated migrations, the CLI config and the link to the hosted project. Anything after `--` is passed through
to the CLI.

| Script | Runs | Use it like this |
|---|---|---|
| `backend:link` | `supabase link --workdir local-backend` | `npm run backend:link -- --project-ref <ref>`. Asks for the database password and remembers the project in `local-backend/supabase/.temp/` (gitignored). |
| `backend:push` | `supabase db push --workdir local-backend` | Run `npm run backend:push -- --dry-run` first and check the list, then `npm run backend:push`. Never add `--include-seed`. |
| `functions:deploy` | `supabase functions deploy --workdir local-backend` | Always name the function: `npm run functions:deploy -- pet-talk`. Only `pet-talk` is declared in `local-backend/supabase/config.toml` (entrypoint `../../supabase/functions/pet-talk/index.ts`, `verify_jwt = true`). |
| `functions:secrets` | `supabase secrets set --workdir local-backend` | `npm run functions:secrets -- --env-file "$PWD/supabase/functions/.env.staging"` (works in bash and PowerShell). Use an absolute path, see Gotchas. |

**Other scripts.**
- `backend:test`: runs the pgTAP suite. Add `-- --linked` to run it against the linked project; every test runs
  inside a transaction and rolls back.
- `backend:dump`: backups, see section 6.
- `start:local` and `start:staging`: profile wrappers around `expo start --clear` (`scripts/expo-profile.js`).
- The old `supabase:deploy:*` and `supabase:logs:*` scripts target the deleted project `gghesvpmskjlrlpoosgf`.
  They're superseded; don't use them.

## 4. A fresh staging project, in order

**Before you start:** Docker is running; Supabase CLI 2.67.1 or newer; you have run `supabase login` with the
account that will own the project; and `npm run check` and `npm run backend:test` pass locally.

1. **Create the project** in the Supabase dashboard (owner), for example `luna-staging`, in a region near the
   testers. Save the database password in a password manager.
2. **Link:**
   `npm run backend:link -- --project-ref <ref>`
3. **Push the schema.**
   - `npm run backend:push -- --dry-run`: it must list exactly the 27 migrations, `20250101000000` through
     `20260927000200`.
   - Then `npm run backend:push`.
4. **Prove the security model on staging:** `npm run backend:test -- --linked`. The expected result is 4 files and
   PASS; nothing is kept.
5. **Set auth in the dashboard**. Don't use `supabase config push`: the local `config.toml` is not staging's config.
   - Email provider on.
   - **Confirm email off.** The app has no "check your email" screen yet.
   - Minimum password length 8.
   - A neutral Site URL.
   - No redirect URLs.
6. **Take the first backup**, before any tester arrives:
   `npm run backend:dump -- --linked`
7. **Set the function secrets**. Needs the owner's go-ahead for OpenAI.
   - Copy `supabase/functions/.env.example` to `supabase/functions/.env.staging`.
   - Fill in `OPENAI_API_KEY`, and optionally uncomment `OPENAI_MODEL`.
   - `npm run functions:secrets -- --env-file "$PWD/supabase/functions/.env.staging"`
8. **Deploy the function:**
   `npm run functions:deploy -- pet-talk`
9. **Point the app at staging.**
   - Copy `.env.example` to `.env.staging`.
   - Fill in the project URL and publishable key from the dashboard's API settings.
   - `npm run start:staging`
10. **Smoke test** with a brand-new test account: sign up → onboarding with a photo → check-in → finish a task →
    garden points → journal entry → Pet tab ("Talk" appears only if step 7 set a key). Then turn on the scheduled
    backup (section 6).

**Why this order.**
- The schema exists before anything reads it.
- The security tests pass before any user exists.
- A backup exists before the first real row.
- Secrets are set before the deploy, so the function's first request already sees its key.
- The app comes last, pointed at a backend that is complete.

## 5. Seed data

| Where | Seed | Contents |
|---|---|---|
| Local | `npm run backend:seed` (`local-backend/seed-demo.js`) | One demo account ("Biscuit"), photos and a week of activity. The login is in `local-backend/README.md`. **Local only.** |
| Staging | **none** | Nothing is needed. See below. |

**Why staging needs no seed.** Everything staging needs arrives with `backend:push`, inside the migrations: the
10-plant catalog, the 5 legacy garden items, and the trigger that gives every new user their 3 default tasks. A
freshly reset database has exactly those rows and **zero accounts**.

**Test accounts on staging** are made through the app's own sign-up, never by a script with a shared password.

**Guards:**
- The demo seed reads only `.env.local` and refuses anything but plain `http` to a private address.
- There is no `local-backend/supabase/seed.sql`, and `[db.seed]` is off.
- `src/__tests__/seedSeparation.test.ts` fails if a migration inserts accounts, contains the demo login or holds a
  key, or if the demo seed loses its guard.

## 6. Backups

The original project was deleted with no backup. These steps are how that never happens again.

**On demand:**

```bash
npm run backend:dump -- --linked                 # staging: roles, schema, data
npm run backend:dump -- --linked --with-photos   # plus every pet photo
npm run backend:dump -- --local --with-photos    # the local stack
```

Each run writes `backups/<target>-<UTC stamp>/` (gitignored) containing `roles.sql`, `schema.sql`, `data.sql`,
`manifest.json` (sizes and SHA-256) and, with `--with-photos`, `storage/pets/…`. **`data.sql` holds real user
data**, including `auth.users`: keep it private.

**What a dump contains:**
- All tables, functions, grants and RLS policies in `public`.
- Every row, including auth users and storage metadata.

**What it doesn't contain:**
- Storage policies and the migration history table: the CLI skips both. Both live in the repo's migrations.
- The photo files themselves: use `--with-photos`.
- Auth settings, function secrets and the functions: those are the dashboard, `.env.staging` and the repo.

A local run on 27 Sep produced 22 tables, 52 policies, 9 functions and 95 grant/revoke statements, plus 3 photos.

**Restore into a new project.** This follows Supabase's CLI restore guide; our drill has not been run yet.
1. Create the project and link it (section 4, steps 1–2).
2. Load the three files, using the session-pooler connection string from the dashboard's Connect panel:
   ```bash
   psql --single-transaction --variable ON_ERROR_STOP=1 \
     --file roles.sql --file schema.sql \
     --command 'SET session_replication_role = replica' \
     --file data.sql --dbname "<session pooler connection string>"
   ```
3. Re-create the storage policies: run `local-backend/sql/pets_bucket_private.sql` in the SQL editor. It is idempotent.
4. Tell the CLI the migrations are already applied, so a later `backend:push` doesn't replay them:
   `npx supabase migration repair --workdir local-backend --status applied <each of the 27 versions>`.
5. Put the photos back, from inside the backup folder:
   `supabase storage cp -r storage/pets ss:///pets --experimental --linked --workdir <path to mobile/local-backend>`.
6. Redo section 4, steps 5, 7 and 8 (auth settings, secrets, deploy).

Run this drill once on a throwaway project after staging exists. A backup that has never been restored is only a hope.

**Scheduled backup (drafted, disabled):** `.github/workflows/staging-db-backup.yml.disabled`.
- **What it does:** a daily dump of staging (roles, schema, data), encrypted with a passphrase and kept as a
  workflow artifact for 30 days. It never writes to the database.
- **Why it doesn't run:** GitHub ignores files that don't end in `.yml`. To enable it, add the secrets, rename the
  file to `staging-db-backup.yml`, run it once by hand, and test-decrypt the artifact.

It needs two repository secrets:

| Secret | What |
|---|---|
| `STAGING_DB_URL` | Staging Postgres connection string including the database password, percent-encoded. Use the **Session pooler** string (port 5432): GitHub's runners have no IPv6, and the direct `db.<ref>.supabase.co` host is IPv6-only. |
| `BACKUP_PASSPHRASE` | A long random passphrase used to encrypt each dump. Keep a copy outside GitHub. |

- **Why the encryption:** artifacts are downloadable by anyone who can read the repository's Actions, which is
  everyone if the repository is public.
- **Photos aren't included.** Adding them would also need `SUPABASE_ACCESS_TOKEN` and the project ref for
  `supabase storage cp`.

## 7. Gotchas

- **Relative paths under `--workdir` are inconsistent.** `db dump -f x.sql` resolves from `local-backend/`, but
  `storage cp` resolves from the directory you run it in, and treats `C:\…` as a URL. Both were verified on 27 Sep.
  Pass absolute paths to `--env-file`, as in section 3.
- **`supabase functions serve` creates an empty `local-backend/supabase/functions/` folder.** It is harmless, and
  git ignores empty folders.
- **Publishable vs legacy anon key.** New projects issue `sb_publishable_…` keys; the local stack uses the legacy
  anon JWT. `EXPO_PUBLIC_SUPABASE_ANON_KEY` takes either. Signing in with a publishable key through
  supabase-js 2.50 is not verified yet: if it fails, use the legacy anon key while it is still issued.
- **Not verified end to end:** `backend:link`, `backend:push`, `functions:deploy` and `functions:secrets` against a
  real project. The deploy config's out-of-tree entrypoint *was* verified with a local `supabase functions serve`,
  which answered `{"name":"pet-talk","configured":false}`.
